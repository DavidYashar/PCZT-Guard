# Proposal: verify `user_address` before signing (librustzcash#3155)

**Status:** draft for the upstream issue. Not yet a pull request.
**Approach:** hand the maintainers a working implementation and a reproducible attack, not
just a complaint.

---

## The gap

`pczt::roles::signer::Signer` checks that each spend's nullifier is consistent with its note
(`spend.verify_nullifier(None)`), and signs. It never checks the **outputs**. An
`orchard::pczt::Output` carries:

* `recipient` — the address the note commitment is built over, and therefore the address the
  money goes to;
* `user_address` — the address the signer displays to the human.

These are independent fields, and nothing in the crate requires them to agree. A constructor
that sets `recipient` to itself and `user_address` to the victim produces a PCZT that passes
every check the Signer runs. `set_output_user_address` is a public API in `orchard`, so this
needs no byte surgery.

The same is true of Sapling and, per the doc comment on
`transparent::pczt::Output::user_address`, of transparent outputs — where the specification
already says a signer "must parse this address (if present) and confirm that it contains
`recipient`". For the shielded pools that requirement is not stated and not enforced.

## Reproduction

The attack is reproducible without Testnet funds, in about 20 lines:

```text
cargo xtask fixtures                      # honest PCZT + attack PCZT, both testnet, post-NU6.3
cargo test -p xtask stock_signer_signs_the_tampered_payment
```

* `xtask::honest()` pays Alice and says Alice.
* `xtask::address_deception()` pays Mallory and says Alice. It is built with the same
  `DeferredPcztBuilder`, so `verify_cv_net`, `verify_nullifier`, `verify_rk` and
  `verify_note_commitment` all pass.
* `Signer::sign_ironwood(...)` on the second one returns `Ok`.

Both tests are in `xtask/tests/attack.rs`.

## Why not just "call the verifier role"

Running every helper the crate exposes does not catch it either — that is the point of the
reproduction above. What is missing is a *comparison*, not a *check*: nothing in the crate
answers "does the address I was told to show actually contain the receiver this output
commits to?"

`zcash_address::ZcashAddress::matches_receiver(&Receiver)` already does the hard part
correctly, including Unified Addresses (where the receiver for the pool has to be selected)
and the fact that Ironwood reuses the Orchard receiver. The missing piece is calling it.

## Proposed API

On `orchard::pczt::Output` (and the Sapling and transparent equivalents):

```rust
impl Output {
    /// Verifies that `user_address`, if present, contains the receiver this output pays.
    ///
    /// Signers should always call this before signing: `user_address` is what the user is
    /// shown, and nothing else ties it to `recipient`.
    ///
    /// Returns `Ok(true)` if `user_address` is present and matches, `Ok(false)` if it is
    /// absent (change is conventionally unlabeled), and `Err(VerifyError::UserAddressMismatch)`
    /// if it is present and does not match.
    pub fn verify_user_address(&self, pool: PoolType) -> Result<Verified, VerifyError>;
}
```

Two details worth deciding together:

1. **Absent `user_address`.** Change outputs are unlabeled by convention
   (`zcash_client_backend` labels only external payments), so "absent" must not be an error.
   It is also not a pass: a signer cannot describe that output to the user. The proposal
   returns it as a distinct value rather than folding it into `Ok(())`.
2. **Ironwood.** It has no address typecode of its own and shares the Orchard receiver, so
   the pool argument is needed to select the right receiver when the address is unified.
   `PoolType::IRONWOOD` does not exist today; mapping Ironwood to `PoolType::ORCHARD` for
   this call is what PCZT Guard does.

In the Signer:

```rust
// pczt/src/roles/signer/mod.rs, per Orchard-family action
spend.verify_nullifier(None)?;
if let Some(output) = action.output().user_address() {
    output.verify_user_address(pool, network)?;   // new
}
```

with an escape hatch for the flows that legitimately need to sign an unlabeled or
deliberately-mismatched PCZT (the restricted builder's dummy outputs are generated by the
builder, not supplied by a constructor, so they should already agree).

## What PCZT Guard will contribute

`crates/pczt-guard-core/src/binding.rs` is a complete implementation of the comparison,
including the padding and redaction cases, the Unified Address receiver selection, and the
distinction between "wrong pool", "not an address" and "different payee". I am happy to
extract it into the shape the maintainers prefer, add it to the existing test vectors, and
open a PR — with the caveat that the code was written during a hackathon and should be
reviewed closely.

## Related, smaller gaps found while building this

* **`zcash_address` 0.14 has no `network_type()`.** A parsed `ZcashAddress` cannot be asked
  which network it belongs to, so a signer cannot check that a `user_address` string is for
  the network the transaction is for. Inferring it from the bech32 HRP is fragile. A
  `network_type()` accessor, or a `matches_receiver_on(network, receiver)`, would close this.
* **`Pczt::value_sum` has no setter and no documentation of its sign convention** in a form a
  third party can check against. PCZT Guard compares the declared value sum against
  `Σ spends − Σ outputs`; a documented invariant (or a `VerifyError` for the mismatch) would
  make that check upstream's rather than every consumer's.
* **`anchor_deferred()` is false on PCZTs built by `DeferredPcztBuilder`.** The builder emits
  a materialised empty-tree anchor rather than an absent one, so the ZIP 374 state is not
  observable from the parsed bundle even though the witnesses are absent. Either the flag or
  its documentation is off.
